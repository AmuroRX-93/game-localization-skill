# 字库压缩与复用

用于统一字体、扩中文字库及扩字后的加载卡死排查。目标是保留语义、字形和排版，减少重复数据与峰值驻留；不是一律降清晰度，也不是删除未在正文中找到的字符。

## 尽量一套字体、一套字库

按以下层次复用，逐层证明兼容性：

1. **字体源统一。** 优先使用用户指定的同一字体家族、版本和必要字重。要求思源黑体时固定相应地区的 Source Han Sans 源文件和指纹，保留许可证；不同地区字形不视为完全相同。统一风格不要求所有界面同字号。
2. **语义码表统一。** 维护 Unicode → 游戏字码 → 字形索引的稳定映射。新增字符复用已有安全码位，不让不同资源自行给同一码位赋不同中文含义。不同渲染器必须分表时，保留统一语义表及明确转换；不能强行混用单字节与双字节入口。
3. **字形与文件复用。** 相同字体源、字符、字号、度量、描边、像素格式和布局的字形直接复用，优先保留已验像素，不重复栅格化。资源按内容、结构和引用去重；相同文件名不足以证明可替换。构建时生成一份规范资源，向必要物理引用分发并逐份校验。
4. **运行时实例复用。** 加载器已有共享槽／缓存时优先沿用。新增共享必须确认引用计数、所有权、加载释放时机、纹理格式和度量兼容；同一文件路径或相同字节不保证只分配一次内存。不要让一个场景卸载另一个场景仍在用的图集。

一套规范字库可以派生少量按需规格；不要为了只剩一个文件，将全字符、全字号打进一张始终驻留的大图集。保留每个必要变体的理由和消费者，记录复用发生在源字体、码表、文件还是实际内存实例层。

## 先盘点需求，再压缩

为每个字体槽／资源建立表：加载入口、消费者、实际字符串、必需字符、动态来源、原字符、像素格式、单字尺寸、字宽／基线、驻留区间。定位菜单、战斗、标题和数值的真实字体选择；不能把全文字符需求当成所有字库的需求。

字符需求包括静态译文、变量最大展开、玩家命名、数字、标点、按钮符号、其他语言入口与回退。动态或间接调用未查清时保留原有覆盖。清除假名、空白字形或正文未出现的字符不属于可靠压缩方法；空格本来就可能没有墨迹。

优先顺序：

1. 复用已有合格字形与内容相同的资源，避免重复生成和无谓规格。
2. 去掉经消费者分析证明不需要的**额外扩字**，尤其是仅显示固定短标题或数字的字体；保留原有覆盖及所需新增中文。若要进一步删除原字符，另行证明所有可达入口。
3. 在格式允许时合并完全相同的字形图像／图集页，同时保留各语义码位、索引引用和 metrics。重排后修正所有 UV／偏移／页索引。
4. 使用该版本加载器确实支持的紧凑像素格式。白色字形常可用亮度＋透明度表示，但必须检查原像素可无损表示、通道顺序、alpha 精度及预乘方式；彩色字形不可盲转。LA8、A8、索引色并非通用支持项。
5. 裁掉透明填充只在尺寸、步长、UV、bearing 和绘制几何都能正确修正时进行。降低字号、分辨率、alpha 精度或改变字形风格属于质量取舍，另列方案，不混称无损压缩。

## 内存预算和格式证明

分别记录磁盘文件、解压后的 CPU 数据、GPU 内部纹理、上传暂存／复制、头表与对齐、同时驻留的资源，以及可用连续内存。字库粗估可用 `Σ(字形数 × 单字宽 × 单字高 × 每像素字节数)`；变尺寸逐字求和，另加 mip、行对齐和表开销。这只是像素数据量，不是游戏实际峰值。

资源文件压缩通常只省磁盘；加载后展开仍占原大小。输入格式从 RGBA8 改为 LA8，也可能只减少源缓冲和传输量：若渲染接口内部格式仍为 RGBA，不能据此声称显存减半。共享文件也未必消除多次加载缓冲。检查该版本加载分支、格式参数和申请长度，不靠扩展名猜测。

格式修改要核对标志位、端序、每像素步长、行跨度、字形数、偏移表、对齐、全局度量、包长度和上层引用。不要照搬其他游戏的标志位或地址。主机 RAM 很大不代表模拟地址空间、游戏堆或最大连续块充足。

黑屏与字库扩张相关时，保留失败构建和现场，分别做“只减少额外字形”“再转换格式”的候选以便隔离。不要同时回退汉化、改模拟器设置和换启动程序。缩小后恢复可支持内存压力判断；没有分配器返回值／调用链，不能声称已定位某次分配失败或越界写。

## 离线检查与运行验收

- 使用独立读回路径比较全部保留字形的解码像素、语义码位、字宽、尺寸、基线和索引引用；验证原覆盖、当前需求与动态字符，不只比较文件大小。
- 对截断、越界偏移、错误计数／步长等坏输入应拒绝处理。封包后逐成员回读，确认未修改分支、名字、顺序和必要填充保持；输入基线不可覆盖。
- 留下源与候选指纹、需求表、压缩前后各层大小、转换依据和复现命令。只生成改变的资源，复用既有未变容器，不因字体调整复制整游戏。
- 获得本轮安装／启动授权后，在同一构建和设置下重走原失败入口，并检查菜单、命名、战斗、失败／战果与多次切换。用户要求延后实测时只做离线检查，明确未测。
- 区分助手实际观察、用户反馈、静态证明和估算。一个场景恢复不代表全游戏最大峰值已安全，字库优化也不等于已增加分配失败保护。

## 实例：Target in Sight 日版 BLJS10002 / VERSION02.00

2026-10-07 的一次候选沿用同一思源黑体源和共享码表，复用原有已验字形。两个固定标题字体曾多灌入 290 个额外字形位置；定位消费者后，只移除这些多余扩字，保留原字符和标题中文，其余七份字体维持覆盖。

九份字体文件总量由 **41,990,784 字节**减为 **23,442,816 字节**；再利用该游戏原生支持的 LA8 输入分支，降为 **11,728,768 字节**（约 40.05 → 22.36 → 11.19 MiB）。全部 3,499 个保留字形的像素和度量独立回读一致；没有重新采样。仅标题子集减少的原始 RGBA 像素数据约 17.69 MiB。

安装后用户反馈原战斗入口黑屏已解决，支持字库扩张造成内存压力的判断；没有捕获具体失败分配调用，也没有全场景峰值证明。LA8 源格式对应的内部纹理仍为 RGBA，文件缩小约 72% 不能当作显存同比缩小。本次复用的是源字体、码表和字形数据，**未实现跨字体运行时纹理指针共享**。这些数量与格式分支只属于本案例，不设为其他游戏的默认参数。
