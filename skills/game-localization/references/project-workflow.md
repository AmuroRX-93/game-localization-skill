# 项目流程：传统分工与 AI 协作

本流程综合传统民间 ROM 汉化、翻译团队校对与现代本地化工具实践，并加入本项目经历过的回归问题。它是可调整的工程方法，不是行业认证标准；小修改只走受影响环节。

## 先建立技术闭环，再扩充译文

| 阶段 | 主要产物 | 进入下一阶段前看什么 |
|---|---|---|
| 立项和基线 | 版本、目标语言、授权范围、来源、初步资源树 | 找到准确输入和实际加载路径 |
| 技术摸底 | 格式／码表／字体／指针说明、未解析清单 | 原样往返成功，明确不可处理部分 |
| 垂直小样 | 几条真实译文＋字形＋贴图／字幕写回 | 能看到新内容，控制码／长度／内存可行 |
| 内容生产 | 稳定 ID 的双语文本、术语表、风格指南 | 可分批审校、可回收、可追踪变更 |
| 工程合入 | 可重建候选、修改白名单、指纹 | 回读内容正确，未改资源保持完整 |
| 语言与功能验收 | 缺陷单、测试矩阵、截图／日志 | 阻断性问题解决或明确限制，证据绑定构建 |
| 冻结交付 | 同源差分／升级包、安装说明、校验 | 干净安装能得到同一构建，远端资产正确 |
| 维护 | 新反馈、回归样例、失效审校清单 | 改源文件和生成器，避免仅修成品 |

传统工作的关键不是反复手工十六进制替换，而是把找码表、导出文本、翻译校对、改图改字库、回填指针、测试发布连接成可靠链条。可参考 [T.R.A.F. 指南](https://wiki.romhack.org/index.php?title=Guide_de_la_traduction_v2) 与 [Atlas](https://github.com/stevemonaco/Atlas)。

## 角色可由同一人承担，责任不可混同

- 工程负责人：负责抽取、格式、回填、性能／内存边界与构建。
- 翻译：负责源文含义、上下文、角色语气与疑点记录。
- 审校：根据原文和上下文复核，不以“模型说没问题”为通过。
- 美术／排字：遵守原 UI 风格、真实可见区及字体许可证。
- 测试：按场景复现，区别语言、显示和功能缺陷。
- 发布维护：保证包、说明、版本和支持范围一致。

这是工作责任表，不授权自动创建其他任务、调用子代理或联系他人。人员少可分时扮演这些角色；独立审校未做时明确记录，不把同一次生成后的自我评价称作独立审校。

## 批次与变更

按场景、功能或资源模块分批，先稳定技术路径再扩大。同批处理相关说话人与上下文，不随机拆句丢失语境。术语／风格决策进入版本化表；源文、上下文、编码映射或字体变化时使受影响检查失效。修一个字体消费者需列出共享引用；修译文无需无故改画质或输入配置。

翻译记忆与术语表互补：前者复用句子，后者统一概念。模糊匹配必须复核差异，尤其数值、否定和变量。CAT 工具辅助校对而不代替情境判断；[OmegaT 官方说明](https://omegat.sourceforge.io/manual-standard/en/chapter.how.to.html) 介绍了翻译记忆复用。

界面技术小样可用长变量、宽字和可辨识标记模拟翻译长度，提前发现硬编码、拼接和裁切；先确保游戏字库与格式能承载测试字符。正式交付必须清除测试标记。这一思路与 [Unity 伪本地化文档](https://docs.unity3d.com/ja/Packages/com.unity.localization%401.4/manual/Pseudo-Localization.html) 一致，不要求为旧游戏安装 Unity。

## AI 的合适位置

| 工作 | 可交给 AI 辅助 | 通过依据 |
|---|---|---|
| 找资源 | 分类、提出格式假说、编写解析器 | 样本、边界检查、往返、加载证据 |
| 翻译 | 有上下文的初稿、术语建议、疑点筛选 | 源文复核与审校结果 |
| 音频／贴图 | ASR、OCR、区域识别、底图修复 | 原声／原图核对和逐字排版检查 |
| 检查 | 找差异、生成测试、汇总清单 | 可重跑报告与实际场景 |
| 交付 | 说明、打包、升级脚本 | 干净安装、回退、构建和远端指纹 |

确定性的偏移计算、编码、哈希、封包边界和 token 约束交给程序检查。开放性的译义与风格让 AI 帮助人判断。AI 不能凭预测替代测试，也不能因不确定就把可完成的工作全部推给用户。

## 面向未来

实时 OCR／语音翻译可能减少玩家“等汉化”的需求，但这与无延迟、术语一致、贴合 UI、可存档、离线稳定的集成本地化不是同一交付。不能给出“两年后一定不再需要汉化”的保证。维护可更换的模型、可复用的术语／适配器与独立验证，比依赖某一代模型的能力承诺更持久。
