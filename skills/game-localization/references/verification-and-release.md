# 验证、交付与维护

## 按证据定位

记录用户症状、准确页面／关卡、输入动作、构建指纹、环境版本、最新日志和截图，区别译义错误、映射错误、排版裁切、错资源、漏加载、内存／封包故障、模拟器兼容。先选能排除一个假说的最小对照，不盲调分辨率、帧率、驱动或重下载。

同配置测试原版与候选，再逐一改变字体、文本、贴图、影片、更新／DLC。原版也崩则不能直接怪汉化；原版正常也不能直接断言一定是译文字节，而应缩小改动集。错误日志是线索，不是因果证明。

路径检查涵盖实际启动入口、大小写、分隔符和虚拟文件系统；宿主系统看得见文件不保证游戏能按请求路径读到。只改一个疑似文件无效不能证明整类假说成立或不成立。

局部 HUD 花屏与某关卡彩色异常分别建复现点，不扩大成“全屏普遍闪烁”。某设置改善一个场景却恶化另一场景时，将两者纳入同一回归对照，记录改善和代价，不能由一次好转确证根因。用户要求回退某项试验时，只撤销该变更并核对当前值，保留后来已采用的译文、换行和 UI 修复；不要拿旧整包覆盖新状态。

## 五层证据

| 层次 | 能支持什么 | 不能支持什么 |
|---|---|---|
| 清单与解析 | 已解析范围、待查资源、稳定 ID | 没有任何遗漏 |
| 语言与显示静态检查 | 控制码、术语、字形、UV／排版候选 | 游戏已读取正确资源 |
| 写回／往返 | 指针和容器可重建、修改范围受控 | 程序不崩、内存足够 |
| 运行 | 某构建在某平台的指定场景通过 | 全版本全平台全关卡通过 |
| 安装与发布 | 接收者能重建目标，远端资产一致 | 所有剧情译义准确 |

每条测试绑定构建哈希；构建变化后按依赖分析使相关测试失效，不能拿旧测试替新构建背书。源码分析、自动检查、用户确认和直接观察分别标注。

## 运行矩阵

按修改影响选择：冷启动、加载复制的游戏内存档、主菜单／设置／按键帮助、最长文字和动态变量、改名、商店／装备、剧情分支、战斗、结算、存读档、返回菜单、退出重进。字体／内存改动覆盖高驻留场景及重复进入；字幕覆盖首次／再次、跳过、结束转场；更新／DLC 测到进入内容、完成结算、保存再读取。

实时语音字幕另按模式、资源组、播放通道和触发类型列覆盖矩阵。先用短诊断文字确认绘制层，再验证真实中文、资源匹配、起止同步及 HUD 遮挡；诊断文字可见、启动日志正确或代表关卡通过，均不证明全模式通讯已可触发。

旧即时存档可能携带旧程序和字体，验证新二进制先冷启动再读游戏内存档。使用测试存档副本。玩家正在游玩时先完成离线工作，重启前保护未保存进度；已有明确退出授权无需重复询问。

独立测试配置也要保留完成测试所需的输入设备：核对手柄处理器、设备与玩家槽、按键映射；复制必要配置到隔离目录后读回，不能以默认键盘配置替代用户正在使用的手柄。启动授权按当前会话及用户偏好判断，已授予的同范围授权不重复询问。此用户要求默认静音测试，启动前验证静音设置。先验证菜单输入确实响应，再判断“无法操作”是输入未接、窗口焦点、卡顿还是游戏崩溃；用户报告卡死仍应作为待查故障保留，不能反过来断言只是手柄问题。

测试矩阵未执行的格子写未测。工具无法控制窗口／按键时不要谎称看到目标页面，可交付明确复现路径请玩家验证。验证报告写观察到的事实，例如“当前已在测试战斗”不能写成“亲自完成了进入、战斗、退出全流程”。

## Git 增量同步规则（2026-10-14 用户要求）

- 每个开发／汉化项目使用独立 GitHub 私人仓库。先查看本地 Git 状态、已有 remote、当前分支及对应远端，优先复用已有私人仓库和完整历史。没有仓库时在用户当前 GitHub 账号下创建 private 仓库，并读回确认可见性。已有公开发行仓库不擅自改可见性或删除；另设私人开发 remote，公开发行按原有授权推进。
- 源码、译文与术语表、资源生成器、补丁／构建／校验／部署脚本、开发说明和必要的自制素材持续入库；每次完成一批实质修改后，审查差异、暂存本任务相关文件、写清变更提交并推送，结束前核对远端分支提交与本地提交一致。无变化不制造空提交。推送失败如实记录本地提交及未同步状态，保留进度下次续推。
- 复用 `.git` 和提交历史，使用正常 `git push` 增量传输。Git 传的是远端缺少的对象／提交并可进行差量压缩，不是简单按文件名判断；不要每轮重新初始化、丢弃历史、强推重建或把工程打 ZIP 当代码同步。遇到远端并行修改先检查并整合，保留他人提交，不用强推覆盖。
- `.gitignore` 排除游戏原版与完整镜像、大型整合／构建包、临时解包和缓存、重复生成产物、个人存档／配置、BIOS、账号凭据及聊天记录。私人仓库也不能夹带密钥和私人数据。开发素材按实际用途与分发权限纳入；必要大型开发资产按需采用 Git LFS，先核对配额和依赖，不默认将游戏镜像纳入 LFS。
- 本地工作树确认不用的开发文件，删除也通过提交同步；旧游戏镜像按清理规则在本地处理。普通删除提交不清除 Git 历史，不能承诺缩小已有远端历史体积；历史重写不属于日常增量推送。
- GitHub Release 的 7z／ISO／分卷附件不走 Git 对象增量协议。只有用户要求发布／更新发行包时才重建上传发生变化的附件；已存在且指纹一致的附件复用，不重复上传不变内容。需要小体积交付时另做经验证的差分包，不能把 Git 增量推送说成大包也能自动续传差分。

## 构建与安装

固定来源指纹、工具版本、译文修订、字体和输出指纹。保存变更清单及必要的重建／恢复材料；回退优先使用原版基线、源文件、脚本或小型差分，不默认保留完整旧版镜像。旧版本按下述用户约定清理。

### 旧版本清理规则（2026-10-14 用户要求）

- 默认只保留一份原版基线和一份最新版游戏镜像。已被替代的旧镜像、失败候选、无用版本、重复备份及不再需要的临时解包／构建副本，在确认无使用依赖后删除；先留记录，不把移入长期备份目录或重新压缩旧版当作清理。
- 删除前在本任务已有清单／交接中记录版本或用途、绝对路径、大小、校验值、淘汰原因、替代版本与路径；删除后记录结果。现有可信哈希可复用，缺失时计算。记录不等于可恢复副本，不宣称仅凭哈希能还原旧文件。
- 核对最新版实际存在且已完成本次要求的验证；用户接受延后手测时，明确未测即可，不以额外验收要求无限保留旧版。仍被进程、下载、构建或其他助手使用的文件先协调，不能仅凭文件日期判断无用。
- 保留存档、个人配置、汉化源译文／源资产／脚本及必要证据；仍被补丁依赖的唯一底座不算无用版本。多轨镜像的必要轨道、尚需齐全的分卷也不能当作重复文件删除。用户明确要保留的最新版整合包按交付物保留，内容与运行镜像相同不自动视为无用。
- 此约定授权在当前游戏工作范围内清理已确认无用的旧版本，无需逐次再问；不扩展为扫描删除其他游戏、修改公开发行或清理他人正在进行的任务。新的保留指令优先。

### 安装与打包验证

重做整合包时从清单和输入哈希可核对的干净发行基线重建，不直接打包正在游玩的实验目录。核对正式补丁包指纹，按修改清单校验旧字节及新字节；构建后再跑同一完整预检／规划器，确认受检查目标已满足，支持重复安装的工具应无剩余改动。这只证明预检覆盖范围内收敛，不能代替游戏运行。

差分应区分原版首次安装和旧汉化升级；支持每个基线哈希，不用模糊文件名判断版本。安装器应预检全部输入、目标版本、空间和写入权限；拒绝未知／混合版本，避免半安装。写临时输出、验证、再提交；失败清理不完整输出。原地多文件安装需持久事务日志和可验证回退，恢复不能覆盖用户之后的修改。

等待玩家退出后安装时，重新核对游戏基线并捕获此时的存档／配置保护快照。玩家在等待期间正常保存造成的变化不能算作安装损坏，但实际安装期间保护文件必须保持不变。进程判断用可执行文件路径和进程身份，避免名称含模拟器字样的辅助脚本导致误报。记录磁盘已安装版本与仍在运行进程所加载的旧版本，资源写入后不能立即声称旧进程已使用新修复。

测试成功路径之外的关键失败：错误基线、缺少分卷、已有目标、路径含中文／空格、只读、空间不足、意外中断、重复安装、还原。备份要校验；不能只用存在文件名证明恢复可用。大型文件流式处理，避免把整套游戏载入 RAM。

随包解释器测试另覆盖移动后目录、不同工作目录及外部 `PYTHONHOME`／`PYTHONPATH` 污染，入口明确隔离外部 Python 环境。用独立小样制造缺失／损坏，要求实际用户校验器非零退出并指出失败文件；不要为负例破坏发行输入。分别记录解释器启动、关键模块导入、文件校验和游戏运行。

## 发布体验

PS2／PS3 的 PC、安卓和实机出口按 [三平台交付方案](platform-delivery.md) 选择：PS3 更新优先验证可生效的 PKG，PS2 以修补镜像为主，7z／ZIP 只承担传输包装。本项目自制安卓更新原型已退役，不再作为安装前置条件。

跨平台安装器把“同一游戏数据可用”和“启动工具可执行”分开验证。附带 Python/其他运行时时，按 Windows 架构、macOS Intel/Apple 芯片或已验证通用二进制确认实际可运行性，保留依赖许可、可执行权限及离线启动说明；只有脚本就不要写成免依赖 APP。Windows/Intel Mac 未执行过应如实列出，不能由 Apple 芯片 Mac 上测试代替。

正式/预发布标签遵循用户已授权的发布决定，不能把技能中的候选默认值当成额外审批要求；真实未测范围继续保留。PS3 ISO 与 CFW/HEN 的专门边界见 [PS3 封装与实机](ps3-packaging.md)。

用户面对的入口保持清楚：当前发行、先读说明、对应平台启动工具、支持版本、回退方式。开发临时文件另放。说明在压缩包里面，不依赖聊天记录；整合版、原版差分、旧版升级不能互相冒充。不要夹带个人存档、BIOS、账户文件或未审查的其他工具；素材分发按实际范围与许可处理。

私人开发仓库的日常推送已按上述用户要求授权；公开发布或上传发行附件仍需对应发布授权。发布前在干净目录从包内说明完成一次安装，核对输出指纹与待测构建；测过哪种操作系统如实标注。发布标候选／测试版并不是免除已知致命缺陷；若用户明确要求带已知限制发布，应醒目标出影响、受影响条件及可用回退。

上传后重新读取远端 release 状态、资产名、大小与可用哈希，必要时下载复核。请求报错可能已经成功，先读状态再重试，不无限追加重复资产。ASCII 资产文件名加中文说明可减少工具兼容问题，但不是平台硬性要求。平台附件限制查当前文档，不把一次经验写成永久数值。

## Windows 安装器报错与包的完整性

“Press any key to continue”只是批处理结尾，先获取它前面的首个错误及日志。区分内置 Python 缺失、解释器启动失败、安装器异常、游戏路径不匹配；不要把每种情况都归因于编码。报缺少 Python 时先对照包清单检查是否只解压了热修文件、是否多套了一层目录、入口相对路径是否正确。热修包如果依赖旧完整包，要明确覆盖到哪个目录；需要独立累计包时，实际携带运行时与载荷并从干净解压目录验收，不能只换文件名。

遇到 GBK／UTF-8 解码异常，定位实际读取边界：文件、子进程输出或控制台输入。自己的文本文件明确约定编码；子进程先保留原始输出字节与退出码，再按已知编码解码，显示日志可使用明确标注的容错策略。不要全局 errors="ignore" 吞掉内容，也不要仅 chcp 65001 就宣称全部编码已修。用可复现失败输出、中文／空格路径和包内解释器验证修复；在 Mac 上运行通过不能替代 Windows 测试。

## 收到新问题

缺陷单包含原文 ID／页面、重现步骤、预期／实际、版本与哈希、证据、影响级别和回归测试。问题修在源译文／源资产／生成器，重新构建；不要只手修发布包。归因确认后增加真正能捕获故障的检查，更新适配器支持范围。
